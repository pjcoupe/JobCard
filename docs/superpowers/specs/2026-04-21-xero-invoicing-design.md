# Xero Invoicing Design (NZ)

Date: 2026-04-21
Status: Approved design for implementation planning
Scope: JobCard WinForms integration to send business-customer invoices to Xero

## 1) Goals

- Add a `Xero` workflow to the existing `JobCard` form for business jobs.
- Allow sending invoices to Xero for jobs where `Business Name` is non-empty.
- Use Xero OAuth 2.0 (not API key).
- Support tenant selection and persistent tenant preference.
- Support two invoice modes via setting:
  - `Draft`
  - `AuthoriseAndEmail`
- Track sent invoice metadata in a new `sentInvoices` collection.

## 2) Hard Constraints

- No implementation should proceed without this approved design.
- Integration targets Xero public APIs with NZ defaults.
- Invoice numbering must use Xero auto-numbering.
- Contact match strategy:
  1. exact business-name match
  2. fallback best-match selector popup with cancel option

## 3) UI Design

## 3.1 Main Form Button

- Add a new `Xero` button:
  - Placement: to the right of `Save Job` and to the left of `Snap Cam`.
  - Enabled only when `jobBusinessName` is non-empty.
  - Opens modal window titled `Xero Management`.

## 3.2 Xero Management Modal

Sections from top to bottom:

1. **Connection**
   - `Connect to Xero` / reconnect button
   - current connection status label
   - tenant selector (if multiple organizations available)
2. **Invoice Mode**
   - toggle slider for `xeroInvoiceMode`
   - values: `Draft` and `AuthoriseAndEmail`
   - toggle writes immediately to settings collection
3. **Customer Check**
   - repeated business name display
   - `Check Customer` button
   - inline status/error label
4. **Invoice Actions**
   - `Send Invoice` button
   - `Delete Invoice` button (shown/enabled only when prior sent invoice exists and action is permitted)
5. **History**
   - existing `sentInvoices` details for current `jobId` (amount, invoice number, date sent, status, etc.)

## 4) Data Model

## 4.1 Existing Settings Collection (`settings.settings`) New Fields

- `xeroClientId` (string)
- `xeroClientSecret` (string)
- `xeroRedirectUri` (string)
- `xeroAccessToken` (string)
- `xeroRefreshToken` (string)
- `xeroTokenExpiresAtUtc` (datetime)
- `xeroTenantId` (string)
- `xeroTenantName` (string)
- `xeroInvoiceMode` (string)
  - default behavior: null/empty/`Draft` => `Draft`
  - `AuthoriseAndEmail` => authorize and email behavior
- `xeroDefaultSalesAccountCode` (string, configurable; initial example `200`)
- `xeroDefaultTaxType` (string, default `OUTPUT2`)

## 4.2 New Collection: `sentInvoices`

One record per successful invoice send/create action for a job in a tenant.

- `jobId` (int)
- `jobBusinessName` (string)
- `xeroTenantId` (string)
- `xeroContactId` (string)
- `xeroInvoiceId` (string)
- `invoiceNumber` (string; assigned by Xero)
- `invoiceMode` (string; `Draft` or `AuthoriseAndEmail`)
- `amountTotal` (decimal)
- `currency` (string; `NZD`)
- `dateSentUtc` (datetime)
- `datePaidUtc` (datetime nullable)
- `status` (string; e.g., `DRAFT`, `AUTHORISED`, `PAID`, `VOIDED`)
- `lineItemsSnapshot` (array/object)
- `rawResponseSnippet` (string optional)

## 5) Xero API Design

## 5.1 OAuth 2.0

- Use Authorization Code flow with refresh token support.
- Required scopes include:
  - `openid`
  - `profile`
  - `email`
  - `accounting.transactions`
  - `accounting.contacts`
  - `offline_access`
- Flow:
  1. User clicks connect.
  2. Browser opens Xero consent URL.
  3. App receives auth code via redirect URI.
  4. App exchanges code for access + refresh tokens.
  5. App fetches connections/tenants and user selects one.
  6. App persists tokens + selected tenant in settings.

## 5.2 Token Lifecycle

- Before each API call:
  - refresh token if near expiry.
  - persist updated token set.
- If refresh fails:
  - mark disconnected state.
  - require reconnect.

## 5.3 Contact Lookup

- On `Check Customer`:
  1. Read `jobBusinessName`.
  2. Attempt exact contact match first.
  3. If no exact match, run broader best-match query.
  4. Show candidate selector popup with cancel.
  5. If user selects candidate, store selected `xeroContactId` in modal state.
  6. If cancel/no valid candidate, keep send disabled and show reason.

## 5.4 Invoice Create/Send

Preconditions to enable `Send Invoice`:

- business name present
- Xero connection valid and tenant selected
- Xero contact resolved
- job total is non-zero
- no existing sent record for same `jobId` + tenant (v1 no resend)

Invoice payload behavior:

- Invoice type: Accounts Receivable (`ACCREC`)
- Currency: `NZD`
- Invoice number: generated by Xero
- Tax type per line: default `OUTPUT2`
- Account code per line: default from settings
- Line items: derived from existing job line fields (`jobDetailXX`, qty, unit, line amount)

Mode behavior:

- `Draft`: create as draft invoice.
- `AuthoriseAndEmail`: create/authorize and trigger email send via Xero API flow.

After success:

- write record into `sentInvoices`
- refresh modal history panel

## 5.5 Delete Invoice (If API Allows)

- Provide delete action only for existing sent invoice record.
- Use confirmation dialog before action.
- Attempt allowed Xero operation for current invoice state (hard delete if supported, otherwise supported reversal/void path).
- Only remove local `sentInvoices` record if Xero operation succeeds.
- On failure, keep local record and display error reason.

## 5.6 Paid-Status Synchronization (Requested)

- Add automatic synchronization from Xero invoice status/payment data back to local records.
- Sync trigger points:
  - on opening `Xero Management` modal
  - after `Check Customer`
  - after `Send Invoice`
  - periodic background poll every 5 minutes while app is open
- For each `sentInvoices` record, query Xero invoice by `xeroInvoiceId` and update:
  - `status`
  - `datePaidUtc` (when invoice is paid)
  - any relevant payment summary fields if available
- When Xero indicates the invoice is paid:
  - update the corresponding job card paid fields (existing JobCard paid model) to reflect paid state/date
  - keep changes idempotent (re-running sync should not corrupt or duplicate state)
- If a paid invoice later changes state in Xero (rare edge case), preserve an audit-safe approach:
  - do not delete local payment history
  - update status fields and append a note/log entry where practical

## 6) Business Rules

- `Xero` button disabled when business name is null/empty.
- `Send Invoice` disabled when total is zero.
- Existing sent invoice for job prevents duplicate send in v1.
- Tenant selection is explicit and persisted.
- `xeroInvoiceMode` always controls behavior.

## 7) Error Handling

- Use inline modal status labels for non-blocking issues.
- Use concise dialog for blocking failures.
- Expected error classes:
  - auth/token failures
  - tenant not selected
  - no customer match
  - invalid invoice payload/account/tax settings
  - API/network errors
  - duplicate-send prevention condition

## 8) Delivery Phases

1. UI shell + settings fields + OAuth connect + tenant selection
2. Check Customer exact + fallback candidate selector
3. Send Invoice + `sentInvoices` persistence + history display
4. Delete/Void behavior (capability-aware)
5. Polish, telemetry/logging, and guardrail improvements

## 9) Acceptance Criteria

- `Xero` button appears at required position and enable/disable logic is correct.
- OAuth connect, token persistence, and tenant selection function end-to-end.
- `xeroInvoiceMode` toggle persists and changes send behavior.
- Customer check follows exact-first then fallback selector with cancel.
- Invoice send blocked when total is zero.
- Successful sends create `sentInvoices` record with expected metadata.
- Existing sent invoice appears in modal and blocks duplicate send in v1.
- Delete/Void only removes local record after successful Xero-side operation.
- Paid invoices in Xero automatically synchronize back and update JobCard paid fields correctly.

## 10) Out of Scope (v1)

- Multi-invoice-per-job resend/versioning flow.
- At-rest encryption hardening for stored OAuth secrets/tokens.
